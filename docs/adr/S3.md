# S3. Changes Appear to All Players Under a Second

**Status:** Accepted
**Design:** [the server loop](../system-design.md#5-the-server-loop-a-500-ms-tick), [real-time sync](../system-design.md#6-real-time-sync), [message contract](../system-design.md#14-message-contract)
**Goals:** [low latency, lean compute, deterministic and recoverable](../goals.md#systems-oriented)

## Context

The brief requires that a change one player makes appears for everyone else within about a second, with no reload. In a strategy game that's also a matter of fairness; every player should see the same events in the same order, and nobody should get an advantage from a client that knows something before the server has decided it. This has to hold on one shared CPU, with players on slow or distant connections, and while the world is busy at the showcase, where a room full of people play at once.

## Options

**Transport**

| Option | For | Against |
|---|---|---|
| Polling | Works everywhere | Two requests a second per client for a 500 ms cadence, and commands still need a second channel |
| Server-sent events plus POST | Simple, plain HTTP | Splits every interaction across two channels, and the server can't tell from the command channel who is still present |
| WebSocket | One ordered channel both ways, and a disconnect means the player has left | Needs reconnect handling |

**Update model**

| Option | For | Against |
|---|---|---|
| Apply each command and broadcast immediately | Lowest latency | Messages per second grow with every command, and there's no single point that orders simultaneous commands |
| Optimistic client: show the result before the server confirms | Feels instant | A slow link can show something that didn't happen, then undo it |
| Batch commands into fixed ticks, one message per client per tick | One order for everyone, one message per client, and bounded latency | Adds up to one tick of delay |

**Tick length**

| Option | For | Against |
|---|---|---|
| 250 ms | Halves the wait | Fixed work per tick runs twice as often, roughly doubling CPU to above the shared CPU's baseline at load |
| 500 ms | Half the brief's second, with room for the round trip, and well within the CPU baseline | Up to half a second before a command applies |
| 1 s or adaptive | Less CPU | A tick plus the round trip would break the one-second requirement, and slowing the tick under load would break it exactly when the room is busiest |

## Decision

One WebSocket per client, and a fixed 500 ms tick on a single server thread. Each tick, the server resolves every event due since the last tick at its exact due time (a fleet arriving at 12.3 seconds arrives at 12.3 seconds, not 12.5), applies queued commands in arrival order ([Persistent, Traceable Execution](S2.md)), writes them to disk, and then sends each client one message with their results and everything that changed in their view. The tick never lengthens under load; if a tick ever risks running long, the fix is to do less work per tick, not to tick less often. The worst case for a change to reach another player is 500 ms of waiting for the tick plus the network round trip, about 0.6 seconds on Australian connections.

The client never decides an outcome. A command shows as pending until the server's result arrives, so a slow connection shows a delay rather than something that didn't happen. Between ticks the client animates from the formulas in the last message ([Compute Pushed to the Client](S1.md)), on server time, which the client keeps in sync from the timestamp on every tick, corrected for the measured round trip. Every client therefore draws the same world at the same moment, and when a tick arrives its values replace what the client drew. If the connection drops, the client keeps animating, reconnects with backoff, and receives a fresh `welcome` with its full view, which is simpler than replaying missed ticks and loads in under a second on slow 4G.

This is fair because every client sees the same commands applied in the same order in the same tick, from one authoritative state, and no client can act on information the server hasn't sent it.

**How many players total?** The load test ran 30 clients on a laptop, with tick processing 14 ms at the median and 20 ms at the 99th percentile, memory peaked at 123 MB, and egress was 42 KB/s. Most per-tick work grows with the number of clients (one view comparison and one message each), so 40 clients should take roughly 19 ms at the median and 27 ms at the 99th percentile, about 130 MB of memory and 56 KB/s of egress. A Fly shared CPU is slower than a laptop, perhaps three times slower, which would put a 40-client tick near 60 to 80 ms. That's still well inside the 500 ms tick, so I expect the server to hold at 40 connected clients. The world itself holds 24 nations (one per Earth start region), so 40 connections means 24 players plus extra tabs and people waiting for a free start. By the same estimate, the first limit to break would be CPU on the shared machine, somewhere past 80 clients. These numbers past 30 clients are extrapolated, not measured on the Fly machine.

## Consequences

- Every command waits up to half a second before it applies, so the game can't support anything that needs reaction times, which suits a strategy game.
- One server thread means no locks and one order to log and replay, but also means all the work of a tick has to fit in one CPU, which is why the per-tick work is budgeted at 20 ms.
- With no optimistic updates, a player on a slow link sees their actions take effect later than others do, but never sees one undone.
- Ties on contested actions go to the faster connection, since commands apply in arrival order.

## Evaluation

- **Enforced** ([game.test.ts](../../spec/game.test.ts), [server.test.ts](../../server/server.test.ts)): one client's command reaches another within one second; a region claimed twice in one tick goes to the first; every tab of one account receives the stream.
- **Enforced** ([client.test.ts](../../e2e/client.test.ts)): another player's arrival shows live at both screen sizes; after a dropped socket the view is restored in under 3 seconds; a pending command changes nothing until the server's result.
- **Measured** ([measurements.md](../measurements.md)): at 30 clients, a claim reached every other client in 277 ms at the median and 501 ms at the 95th percentile (target 600 ms), and tick processing took 20 ms at the 99th percentile (target 20 ms). The laptop numbers still need rerunning against the Fly machine.
