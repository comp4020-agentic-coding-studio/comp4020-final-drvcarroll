# S4. One Stack

**Status:** Accepted
**Design:** [stack](../system-design.md#2-stack), [repo layout](../system-design.md#3-repo-layout)
**Goals:** [all systems goals](../goals.md#systems-oriented)

## Context

The stack had to meet every requirement in the other three system ADRs at once. The client has to reproduce the server's formulas exactly between ticks ([Compute Pushed to the Client](S1.md)). The rules have to be deterministic so the command log replays to the same world, and storage has to fit on one volume with no database server ([Persistent, Traceable Execution](S2.md)). The server has to run a 500 ms tick and hold dozens of WebSockets on one shared CPU and 256 MB ([Changes Appear to All Players Under a Second](S3.md)). On top of that, the balance work relies on a headless sim running thousands of games with exactly the same rules as the live server, and most of the code would be written by agents, so the codebase had to be one that an agent can hold in context and check with types and tests.

## Options

| Option | For | Against |
|---|---|---|
| Different languages for server and client (e.g. Go or Rust server, TypeScript client) | Faster server, lower memory | The rules would exist twice, and any difference between the two copies shows players something that didn't happen; the sim would need a third copy or a binding |
| A game engine (Unity, Godot) exported to the web | Rendering and tooling built in | Large downloads, poor fit for a phone browser, and the server still needs its own copy of the rules |
| A full-stack web framework (Next.js, Remix) | Conventional, lots of help online | Built for request and response pages rather than a long-running tick loop and WebSockets, and adds memory and build overhead the game doesn't use |
| TypeScript everywhere, with one pure rules module shared by server, client and sim | One copy of the rules, one set of types for the protocol, and one language for agents to work in | JavaScript is slower and heavier than Go or Rust, so the server has to be careful with memory and CPU |

## Decision

TypeScript everywhere. The game rules sit in one folder, `rules/`, which imports nothing outside itself, has no I/O, no clock and no randomness, and takes time as a parameter. The server, the client and the sim all import it, so the client draws between ticks with the same functions the server uses to decide, the sim balances exactly the game players play, and replaying the command log gives exactly the same world. The message protocol is defined once in `rules/protocol.ts` as TypeScript types, used by both sides, and the server also checks every incoming message against a schema at runtime, since a client can send anything.

Each layer was picked for the constraints:

- **Server:** Node 24, running `.ts` files directly with no build step. Hono for HTTP, since it's small with a low memory footprint, and `ws` for WebSockets, the reference Node implementation with low memory per socket.
- **Database:** SQLite through Node's built-in `node:sqlite`, so there's no database server and no native module to compile. Its calls are synchronous, which fits a single-threaded server that applies commands one at a time ([Persistent, Traceable Execution](S2.md)).
- **Client:** Three.js for the 3D scene, used directly so I control the render loop and GPU memory, and Preact with signals for the HUD, a 4 KB library where only the numbers that change are redrawn, which matters with six stock counters updating every frame. Vite builds it, with content-hashed file names so browsers can cache assets permanently.
- **Passwords:** scrypt from Node's built-in crypto module, with no native dependency.

Having one language and one rules module also suits agent-driven development. An agent working on the client can read the rules it depends on directly, the compiler catches a protocol change that one side hasn't caught up with, and the same test runner (Vitest) covers the rules, the server, the sim and the black-box checks in `spec/`.

## Consequences

- Node uses more memory than Go or Rust, with about 60 MB used before the game does anything, so the server runs with a capped heap and avoids per-socket compression to stay inside 256 MB ([Compute Pushed to the Client](S1.md)).
- The rules can never touch the database, the network or the clock, so anything that does (chat, logging, accounts) has to live in the server instead, outside the rules.
- One shared module means a change to the rules changes the server, client and sim together, which is the point, but also means a rules change can break all three at once. The tests run against all of them on every push.

## Evaluation

- **Enforced** ([purity.test.ts](../../rules/purity.test.ts)): a source scan fails if anything in `rules/` imports I/O, reads the clock or uses randomness.
- **Enforced** ([economy.test.ts](../../rules/economy.test.ts), [apply.test.ts](../../rules/apply.test.ts)): the state is identical whether advanced every tick, as the server does, or only between commands, as replay does, and replay through a JSON snapshot gives the same world.
- **Simulated** ([balance.test.ts](../../sim/balance.test.ts)): the same seed replays identically, so the sim's balance results apply to the live game.
- **Measured** ([measurements.md](../measurements.md)): at 30 clients the Node server peaked at 123 MB with a 19 MB JavaScript heap, well inside the 256 MB machine.
