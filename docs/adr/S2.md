# S2. Persistent, Traceable Execution

**Status:** Accepted
**Design:** [persistence](../system-design.md#4-persistence-command-log-plus-snapshots), [the server loop](../system-design.md#5-the-server-loop-a-500-ms-tick), [accounts and sessions](../system-design.md#9-accounts-and-sessions), [logging](../system-design.md#11-logging-and-the-live-view-crit-10), [deploy](../system-design.md#12-deploy)
**Goals:** [every event tracked, deterministic and recoverable, isolated and safe, observable, never lose progress](../goals.md#systems-oriented)

## Context

The world is meant to last for weeks ([Endless Play](G5.md)), on a machine that stops whenever nobody is connected and restarts on every redeploy, so nothing a player does can depend on the server staying up. Every accepted action has to survive a restart, and when two players act at the same moment, the order their actions are applied in has to be fair and recorded. Players also have to be told apart securely and stay signed in, and when something goes wrong, I need to be able to work out what happened from the records alone, without having been watching.

## Options

**Storage**

| Option | For | Against |
|---|---|---|
| A JSON file, rewritten on every change | No dependencies | No atomic writes, so a crash mid-write can corrupt the whole world, and rewriting everything on each change is slow |
| Postgres | Robust and familiar | Needs a separate database server, which the one-machine setup doesn't allow, and its memory use is too much for 256 MB |
| SQLite, built into Node, on the volume | No server and no native module to compile; writes are atomic; synchronous calls fit a single-threaded server | One writer at a time, which is fine since the server only has one |

**What to store**

| Option | For | Against |
|---|---|---|
| Save the current state only | Simple | No history, so nothing can be replayed or investigated |
| An append-only log of every accepted command, with periodic snapshots | Replaying the log rebuilds the world exactly; the log is also the activity history; real games can be fed into the sim | The rules must stay deterministic and versioned, or old commands replay differently |

**Ordering simultaneous commands**

| Option | For | Against |
|---|---|---|
| First in, first served, by arrival | One order to log and replay, and easy to explain | A player on a faster connection wins a tie |
| Round robin, one command per player in turn | Removes the advantage of a faster connection on contested actions | More complex, and the order depends on queue state rather than time, which is harder to explain to a player who lost a tie |
| A thread per player | Looks concurrent | One shared CPU means threads take turns anyway, each thread costs a separate JavaScript engine's memory, and shared state needs locks |

## Decision

The world is stored in SQLite on the Fly volume, as an append-only log of commands with a snapshot every 60 seconds and on shutdown. The server keeps the world in memory as one state object. Each tick, it applies the queued commands in the order they arrived, inside one database transaction, and appends every accepted command to the log. The transaction is written to disk before anyone hears about any of it, so a player is never told about an action the server could later lose. On boot, the server loads the latest snapshot, replays the commands logged after it, and advances to the current time. Because the rules have no randomness and no clock of their own, replay gives exactly the same world. A world created under an older version of the rules is closed rather than replayed under the new ones.

Commands are applied first in, first served. Contested actions are rare (two Colony Ships for one region, for example), first in is the order a player expects, and the tie-break is recorded, so a player who loses one can be shown why. Each player can send at most ten commands per tick, which stops one player from filling the queue. A command repeated after a dropped connection carries the same client id and only applies once.

Accounts are a username and password. Passwords are hashed with scrypt, with at most two hashes running at once to stay within memory. Sessions are a random token in an `HttpOnly`, `Secure`, `SameSite=Lax` cookie with a 30-day sliding expiry, and only the token's hash is stored. The WebSocket checks the same cookie and the request's `Origin`, and failed logins are rate limited per username and per IP. There's no email and no password recovery; the game only needs to tell players apart.

Every player action is written to stdout as one JSON line, with who did it, what, the result or rejection reason, and how long it took, along with logins, connects and disconnects. An admin page streams live statistics (players online, commands per minute, rejections by reason, tick time and memory). The command log in the database holds the same history permanently.

## Consequences

- The rules have to stay pure, with no I/O, clock or randomness, or replay breaks. A test scans the rules folder for any of these and fails if it finds one.
- Changing the rules means closing the current world, since old commands can't safely replay under new rules. Accounts and empire names carry over, but progress doesn't.
- One fsync per tick (rather than per command) keeps writes fast, but the server has to rebuild from the log if a commit ever fails, so the state in memory and the log never disagree.
- First in, first served gives a small advantage to the player with the faster connection on a contested action. I accepted this as the cost of an order that's simple to log, replay and explain.
- Chat is stored in its own table rather than in the command log, since it doesn't change the game state, and an admin reset clears it.

## Evaluation

- **Enforced** ([server.test.ts](../../server/server.test.ts)): the world persists across a restart; a repeated client id applies once; a region claimed twice in one tick goes to the first, and the second gets a "taken" rejection; the eleventh command in a tick is rejected; common passwords are refused; the cookie is `Secure`, `HttpOnly` and `Lax`, and only hashes are stored; failed logins return 429 after the limit; a foreign `Origin` is refused; every action writes one JSON log line, never containing a password or token.
- **Enforced** ([apply.test.ts](../../rules/apply.test.ts), [purity.test.ts](../../rules/purity.test.ts), [game.test.ts](../../spec/game.test.ts)): replay gives identical state; the rules contain no I/O, clock or randomness; a command is still there after a fresh login.
- **Measured** ([measurements.md](../measurements.md)): appending a command takes 0.6 ms at the 99th percentile, each stored command averages 111 bytes, and boot (snapshot plus replay) takes under 3 ms, against a limit of one second.
- **Judged** ([checks.md](../checks.md)): reading only the JSON log lines from a 30-player load test, with no database or screen, I could tell the story of the world from boot to the end of the run.
