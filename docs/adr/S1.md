# S1. Compute Pushed to the Client

**Status:** Accepted
**Design:** [constraints](../system-design.md#1-constraints-that-shape-everything), [real-time sync](../system-design.md#6-real-time-sync), [server efficiency](../system-design.md#7-server-efficiency-budget), [client rendering](../system-design.md#8-client-rendering-budget), [message contract](../system-design.md#14-message-contract)
**Goals:** [lean compute, lean network, fast on ordinary hardware](../goals.md#systems-oriented)

## Context

The game has to run on the course provided hardware of one Fly.io machine with a single shared CPU, 256 MB of memory and one storage volume, which stops when nobody is connected. The game itself is heavy, though. It's a 3D solar system with 25 textured bodies, thousands of decorative asteroids, fleets moving along transfer arcs and stock counters ticking every frame, for up to 24 nations at once. A server that small can't draw any of that, or even send it frame by frame, so I had to decide what the server computes and sends, and what each player's browser works out for itself.

## Options

| Option | For | Against |
|---|---|---|
| Server renders or streams frames | Thin client, works anywhere | Impossible on one shared CPU and 256 MB, and bandwidth grows with every player and every frame |
| Server sends the full world every tick | Simple, the client just draws what it receives | Large messages, wasted bandwidth on slow links, and every client receives other nations' private data |
| Server sends a compact, per-player state twice a second; the client draws everything in between | Small messages and little server work, and each player only receives what they're allowed to see | The client has to reproduce positions and counters exactly between messages, so both sides need the same formulas |

## Decision

The server only runs the game rules and sends each player their state. It never draws anything. All rendering happens in the browser.

The game state is stored as compactly as the time model allows: stocks with their rates of change, build and research queues with start times and durations, fleets with their launch time, arrival time, origin and target, and a queue of scheduled events. Planet positions aren't stored at all, since they're a function of time. This keeps the whole world under 5 MB of memory, and it means the client can compute everything between two messages from the same numbers: a stock counter is its value plus rate times elapsed time, a fleet's position is a point along its transfer arc, and a planet's position comes from the same orbit function the server uses. When the next message arrives, the client replaces whatever it drew with the server's values.

The message protocol is designed around that. On connecting, a player receives one `welcome` message with their full view of the world. After that, every 500 ms, they receive one `tick` message holding only what changed since the last one: their command results, public news and scores, changes to anything they can see, and their own private stocks and queues. The server compares each player's view entity by entity with what it last sent them, so a quiet tick is a few hundred bytes. Each player's view is filtered by fog of war before it leaves the server, so a client never receives data about regions or fleets the player can't see, and there's nothing in the browser for a player to dig out. All message types are defined once in a shared TypeScript file and checked against a schema on arrival ([One Stack](S4.md)).

On the client, the rendering is budgeted to run on an ordinary laptop with integrated graphics and on a phone. The whole scene uses about 40 draw calls; asteroids are moved by the GPU rather than by JavaScript; regions are picked by reading a colour from an index image instead of testing a mesh per region; and real planet textures stream in after the first view, at full resolution only for the body the player is looking at. The client starts at the highest quality tier and steps down a tier if frames take too long, and never steps back up, so the quality doesn't flicker between tiers.

## Consequences

- The client is the larger and more complex half of the code, and it has to match the server exactly; a formula that differs between the two shows something that didn't happen until the next message corrects it. Sharing one rules module between them prevents that ([One Stack](S4.md)).
- WebSocket compression is turned off, since each compression context costs hundreds of KB per socket, which doesn't fit in 256 MB. The messages are small enough without it.
- Planet textures add 6.6 MB to the image and download once per visitor, which is a cost on a slow first visit, so the scene first draws with procedural surfaces and loads the real textures after it's interactive.
- Because the server's work per tick is small, the machine can stop when nobody is connected, and the world catches up from stored state when someone returns ([Endless Play](G5.md)).

## Evaluation

- **Enforced** ([game.test.ts](../../spec/game.test.ts)): `welcome` stays under 60 KB, a quiet tick under 500 B and a busy tick under 3 KB; a client never receives another nation's private state or anything about bodies it has no vision of.
- **Enforced** ([client.test.ts](../../e2e/client.test.ts)): the first view loads in under 3 MB, with the real textures streaming in afterwards; a pending command changes nothing on screen until the server's result arrives.
- **Measured** ([measurements.md](../measurements.md)): at 30 clients, server memory peaked at 123 MB (limit 180 MB), tick work took 2.9% of the 500 ms budget, quiet ticks were 356 B and busy ticks 2.5 KB at the 95th percentile, and total egress was 42 KB/s.
- **Measured** ([checks.md](../checks.md)): 60 fps on an integrated-graphics laptop at every quality tier, using under 300 MB of GPU memory; on a software-rendered GPU the client stepped down to the lowest tier within seconds and stayed there.
